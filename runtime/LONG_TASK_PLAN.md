# Ikaros 长任务开发计划

日期：2026-09-07。状态：**阶段一已实现并通过 Linux 本地检查；阶段二至四待实现**。

阶段一交付了当前唯一的运行记录、模型容量配置、托管进程最小链路，以及桌面的调用计数、耗时和基础命令状态显示。最新修订取消任务调用次数和总时长上限，删除输入框中的任务执行上限入口。验证情况见 [阶段一验收记录](LONG_TASK_STAGE1_VALIDATION.md)。Windows CI 和两平台真实 Provider 的整体验收尚未执行。

本计划定义下一轮新增功能和实施顺序。项目当前没有外部用户，采用破坏性重构：直接替换不合适的设计，不承担旧版本代码、协议和开发数据的兼容义务。

## 1. 这一轮要做成什么

用户交给 Ikaros 一项需要多步操作的工作后，它能持续推进、接受中途补充、等待命令结果，并在结束前检查是否还有遗漏。

例如：

> 检查这个项目，修改几处问题，运行测试；测试期间补充一个要求，Ikaros 按新要求继续修改，最后说明改了什么、验证了什么、还剩什么。

本轮交付六项能力：

| 功能 | 用户能得到什么 |
| --- | --- |
| 可控的持续执行 | 复杂任务可以连续执行；能看到时间和模型调用消耗，也能随时停止 |
| 自动上下文压缩 | 对话和工具记录变长后自动整理上下文，保留目标、进度和关键证据 |
| 运行中补充要求 | 不必停止任务，就能发送纠正或追加要求，并看到何时进入执行 |
| 长命令管理 | 命令运行期间继续处理其他工作，随时查看日志、等待结果或停止命令 |
| 完成前检查 | 结束前处理未应用要求和命令结果；发现明确遗漏时继续工作 |
| 中断后继续 | 失败或重启后保留执行事实，下一轮能先核查不确定结果，再继续处理 |

## 2. 开发原则：直接重构，不做旧版兼容

这是当前项目的开发政策。先前文档中的兼容要求只作为历史记录，不约束本轮实现。

- **只维护一种当前实现。** 删除旧输入格式、旧选择器、旧协议解析和按版本分发的执行路径，不再增加 V1/V2/V3 并行体系。
- **直接重建开发数据。** 不做旧数据库迁移、旧事件转换或旧 queued Run 续跑。切换存储结构时重建 Ikaros 的开发状态库；项目文件和模型凭据不属于重置范围。
- **Runtime 与 Desktop 一起升级。** 同步修改协议、生成类型、preload、IPC 和界面，不保留旧客户端适配层。
- **新接口直接替换旧接口。** 新进程管理器替换 `process_run`，删除旧执行器和只为兼容它存在的包装。
- **允许重组模块和数据结构。** 旧类名、表结构、层次和冻结方式都不构成限制；按新职责重新组织。
- **删除失效测试，补齐新行为测试。** 不为已经废弃的行为保留分支，也不靠跳过仍然有效的测试交付。

新版本产生的数据仍必须可靠：正常重启可以恢复记录，重复请求不会重复执行，历史查询不会重放命令。这些是本轮功能要求，与读取旧版本数据无关。

## 3. 具体增加哪些功能

### 3.1 可控的持续执行

**界面增加：**

- 模型设置中的上下文窗口、最大输出配置。
- 会话中的运行状态、已运行时间、模型调用消耗，以及独立的停止按钮。

**执行规则：**

- 删除固定 16 步和 48,000 字符的运行限制，按模型窗口计算输入容量。
- 不设置任务总调用次数、总时长或固定模型步骤上限。任务可持续执行到完成、用户停止或明确失败。
- 主模型、压缩、完成检查、失败请求和显式重试全部记录调用尝试；计数用于展示和核查，不触发任务终结。
- 时长从真正开始执行时计量，排队时间单独显示；压缩和命令等待也计时。
- 开始执行前确定本 Run 的模型、工具、项目、模型窗口及输出预留，中途修改设置影响后续 Run。
- 保留手动停止、单次 Provider 请求的连接/响应/流空闲超时，以及有时限的进程和网络资源清理。取消或失败后报告已知结果和未完成事项。
- Provider Adapter 一次调用只发送一次请求，不隐式重试。后续压缩或完成检查失败时使用明确的退出规则，不能因为取消总上限而无限重试。
- 匹配模型的 tokenizer 优先；无法精确计量时使用明确标注的保守估算。未知 usage 不按零处理。

模型容量按模型规格初始化：已知 DeepSeek V4 模型使用 1,000,000 token 窗口和 64,000 token 输出预留；64,000 是 Ikaros 的初始请求设置，并非官方最大输出（384K）。未知模型暂用 32,768 / 4,096，允许手动修改。规格依据见 [模型容量参考](MODEL_CAPACITY_REFERENCES.md)。

### 3.2 自动上下文压缩与原文检索

**用户体验：** 任务运行期间自动整理过长的上下文；界面短暂显示“正在整理上下文”，随后继续原任务，无需用户另发“继续”。

压缩后保留四类内容：

| 内容 | 保留方式 |
| --- | --- |
| 用户要求与纠正 | 保留原文或可定位的原文引用，不能只依赖模型转述 |
| 已完成工作与待办 | 用摘要记录目标、进度、剩余工作和下一步 |
| 执行事实 | 从运行记录取得文件路径、工具调用 ID、进程 ID、退出码和未知状态 |
| 最近执行细节 | 保留最近完整的工具调用与结果；更早记录可以按引用找回 |

**增加的能力：**

- 在准备下一次模型请求前检查容量；没有未结算工具批次时才进行压缩。
- 初始在可用输入容量达到 **75%** 时触发，目标降到 **50%** 以下。系统指令、工具定义和输出预留也参与完整请求预算。
- 同时支持整理先前对话和当前 Run 已完成的步骤，支持同一任务多次压缩。
- 新增只读工具 `history_read`，按记录 ID 读取当前会话可见的原始片段及相邻工具结果。
- 超长工具输出先保存可捕获原文，模型只接收有界片段和引用；保留省略提示。
- 原始执行记录持续保存；压缩只改变后续模型看到的输入。

**必要约束：**

- 采用当前 Provider/Model 的普通摘要请求，支持不同模型服务。
- 摘要不改写真实退出码或执行状态，不把未知结果写成成功，也不成为系统指令。
- Memory 继续独立管理和计量；压缩不额外复制 Memory 正文、文件预览或历史差异正文。
- 摘要生成失败或没有压缩收益时不反复重试；原上下文仍能装入才继续，否则报告原因和已知进度。
- 每次压缩记录其来源范围。取消或超时后的迟到摘要不能覆盖有效上下文，也不能吞掉期间新收到的补充。

### 3.3 运行中补充要求

**界面增加：** 运行时仍可在输入框发送消息；发送补充和停止执行是两个独立操作。

例如，命令运行时输入“测试结束后再检查中文路径”，任务会在下一次模型处理前收到这条要求。

**处理规则：**

- 新增 `run.steer`，明确指定当前 Run，并携带客户端请求 ID。
- 补充先落盘，再回复接收成功；重发同一请求返回同一结果。
- 多条补充按顺序进入下一次模型输入，不修改已经发出的请求。
- 界面区分“已收到，等待处理”“已纳入第 N 步输入”和“本次未处理”。纳入输入不等于模型已经完成要求。
- 正在执行的命令继续运行；等待命令的操作可以提前返回，让模型尽快处理补充。
- 请求指向已经结束的 Run 时，不转发给另一个 Run。未接收的内容保留在草稿中。
- 完成与接收同时发生时，由一次原子状态判断决定结果；已接收的补充不能静默丢失。

### 3.4 长命令管理

**替换现有命令工具，统一提供：**

| 工具 | 用途 |
| --- | --- |
| `process_start` | 启动命令，返回稳定的进程 ID；无需等命令结束 |
| `process_read` | 查询状态，按游标读取新增日志 |
| `process_wait` | 等待结果或新日志；等待窗口到期后返回当前状态 |
| `process_stop` | 终止指定进程及其子进程 |

**界面增加：** 命令卡片显示运行状态、日志、真实退出码和停止入口；日志过长时可以继续读取。

**生命周期：**

- 命令属于启动它的 Run。启动身份由 Runtime 提供，模型不能自行指定所有者。
- 启动请求或确认消息重复时，返回已有进程记录，不再次启动命令。
- 启动成功只表示命令已启动；等待到期只表示本次等待结束。两者都不表示命令执行成功。
- 命令状态、日志是否收齐、资源是否清理完成分别记录。父进程退出但子进程仍持有输出管道时，也要有界结束等待。
- 日志持续读取并设磁盘与单次输出上限，处理 UTF-8 分块、敏感内容过滤和稳定游标。
- Run 结束、取消或正常关闭 Runtime 时清理所属进程树，覆盖 Windows 和 Linux。

本轮进程不跨 Run 保留，因此开发服务器在任务结束时也会停止。跨轮常驻服务属于后续功能范围。

### 3.5 完成前检查

模型给出最终回答后，先进入“检查结果”，再决定是否结束。

**第一层：Runtime 检查确定的事实。**

- 是否还有已接收但未进入模型输入的要求。
- 是否还有需要处理的进程结果或未清理的进程。
- 是否已经取消或明确失败。

有待处理工作且任务仍在运行时回到主循环；需要停止时明确说明剩余工作。模型上下文装不下时按压缩规则处理，不能通过无限重试规避容量限制。

**第二层：最多一次模型完成检查。**

- 对实际执行过文件写入或命令的 Run，检查用户要求、候选回答与现有证据是否一致；纯问答不增加调用。
- 复用当前模型，不提供执行工具。输出“可以结束”“仍需继续”或“需要用户输入”，附具体缺口和证据引用。
- 若发现明确遗漏，在原 Run 内继续工作；继续后不再次启动检查，避免循环自审。
- 检查失败或证据不足时显示未验证事项，不能伪造“测试通过”。
- 检查期间收到新要求时，旧的结束建议失效；仍然优先处理新要求和取消。

模型检查用于减少提前收尾，真实验证结果仍来自文件与命令记录。需要用户补充时提出问题并结束本 Run，用户回复后正常开始下一轮。

### 3.6 中断后继续

**新版本自身的执行记录必须支持重启恢复：**

- 保存用户输入、补充要求、模型调用、工具结果、压缩记录、已落盘日志和文件差异。
- 重启后显示已完成内容、失败原因，以及哪些操作的结果无法确定。
- 崩溃时仍在运行的命令标为未知；不根据旧 PID 认领进程，也不自动重新执行命令。
- 用户在同一会话继续提要求时，模型能看到这些事实，并核查磁盘或命令结果后继续。
- 未执行的排队请求可以按当前格式恢复；升级前留下的旧格式请求直接废弃。

这项功能交付的是“记录可恢复、工作可继续”。跨 Runtime 重启保持活进程运行不在本轮范围内。

## 4. 核心设计如何重构

先统一运行记录，再在上面实现功能，避免一个事实被多个快照和 manifest 重复表示。

| 核心记录 | 单一职责 |
| --- | --- |
| `RunConfig` | 保存本次执行确定的模型、项目、工具能力、上下文窗口和输出预留 |
| `InputRecord` | 按顺序记录用户初始输入和运行中补充 |
| `ContextRevision` | 统一表示初始上下文与每次压缩后的上下文，包含摘要和原始记录引用 |
| `StepInput` | 记录某一步实际使用的上下文 revision、输入范围和预算结果 |
| `ModelCall` | 统一记录主模型、压缩、完成检查的调用尝试、usage 和结果 |
| `ProcessSession` | 保存命令身份、所属 Run、日志位置、退出与清理状态 |

当前使用 Session schema 11、Journal schema 8 和协议 5；只接受这一种格式，不提供旧版本迁移。

这些是数据职责，不要求为每一行建立独立的 Service 或数据库。

**直接替换的旧设计：**

- 删除 `ContextSnapshotV1/V2`、旧历史选择器及其双版本解析；初始输入和压缩输入使用同一种结构。
- 合并 SubmissionFrame、RunManifest 等重复表达执行配置的结构；步骤记录引用配置，不复制多份。
- 去掉“一个 Run 只能有一份上下文”“只能有一条用户输入”的限制。
- 用一个进程管理器替换旧 `process_run` 的同步执行与清理逻辑。
- 删除相关旧格式迁移、兼容测试和执行适配层；当前格式标识仅用于检测过期数据。

**新内核统一保证：**

- Journal 记录已发生的事实，界面和查询投影可以重建。
- 模型请求、压缩和进程启动在数据库事务外执行；接收、结算和终结状态原子落盘。
- 发出外部操作前记录其稳定身份；结果未确认时保留未知状态，避免自动重复执行。
- 输入整理、历史读取与工具调度分开；读取历史永远不会触发旧操作。

现有模型设置、Memory、Skills、文件预览和差异功能需要继续可用；内部实现和协议允许一起重构。

## 5. 实施顺序与每阶段交付

### 阶段一：重构运行内核与模型容量

**实现：** 单一当前数据结构、初始 ContextRevision、统一模型调用记录、模型窗口配置和新协议；删除旧版兼容路径，重建开发状态库。

**交付：** 一次普通“读文件 → 修改 → 执行命令 → 回复”任务可在新内核完成；模型设置可配置容量，界面显示调用次数与耗时，停止和错误处理正常工作。命令执行先走新进程管理器的最小完整链路，下一阶段补齐长命令交互。

**过关条件：** 从空库运行、当前格式重启、重复提交、配置快照、连续执行超过原调用上限、Provider 超时和取消通过测试；工程中不再同时维护两套执行模型。

### 阶段二：长命令与运行中补充

**实现：** 完整的进程启动/读取/等待/停止工具、日志卡片、运行时输入框及 `run.steer`；同时实现补充接收与终结的原子判断、进程结果处理和退出清理。

**交付：** 启动验证命令后继续修改其他文件，中途追加要求，收到命令结果后按新要求完成后续操作。

**过关条件：** 等待、补充、停止互不混淆；重复请求和断线重试不重复执行；两平台的进程树和日志资源可以清理。

### 阶段三：自动压缩与历史检索

**实现：** 上下文容量检测、摘要生成、追加压缩后的 ContextRevision、事实保留和 `history_read`。

**交付：** 同一 Run 经多次压缩后继续工作，必要时找回早期命令、错误和用户要求的原文。

**过关条件：** 多次压缩、摘要失败、无压缩收益、超大工具输出和取消竞态通过测试；压缩后的实际模型请求包含应有事实。

### 阶段四：完成检查与整体交付

**实现：** 整合前面阶段已有的终结检查，增加一次模型核对、状态与未完成事项展示；贯通失败和重启后的继续处理。

**交付：** 用户可以交付一项完整的多步骤工作，看到执行、补充、等待、核对和最终结果。

**过关条件：** 完成下列整体验收。提前收尾、无限等待、重复执行和静默丢失补充都必须有对应回归用例。

每个阶段形成独立提交，完成该阶段的真实链路后再推进。现有 UI 改动单独整理，避免混入运行内核重构。

## 6. 怎样确认这一轮完成

| 场景 | 必须观察到的结果 |
| --- | --- |
| 多步骤文件任务 | 连续至少 30 个主模型步骤、两次压缩后仍能完成任务，关键约束没有遗失 |
| 压缩后找回证据 | 能读取早期失败命令及准确错误，依据原文继续处理 |
| 长命令期间补充 | 日志持续可见，补充被纳入后续请求，命令不被重复启动 |
| 模型提前收尾 | 构造尚有验证工作却给出最终回答的轨迹，完成检查能指出缺口并继续 |
| 断线与重复发送 | 初始提交、补充和进程启动均不重复落地；确认消息丢失后可以重试 |
| 崩溃后继续 | 已写文件和已落盘差异保留；未知操作先核查，不自动重跑 |
| 持续执行与停止 | 超过原调用次数和时长上限仍可继续；手动取消与单次请求超时能结束等待并完成有界清理 |
| 压缩或检查失败 | 保留已知进度和原因；不无限重试摘要，不循环启动完成检查 |
| 正常问答 | 不触发多余的完成检查，答案完整后正常结束 |

工程门禁覆盖 Windows/Linux：Runtime pytest、Ruff、严格 mypy、协议生成检查；Desktop 类型检查、Vitest 和生产构建。

此外，两平台分别使用真实 Provider 和隔离项目实测：多文件修改、长命令加中途补充、崩溃后继续。记录任务结果、人工纠正、调用次数、usage、耗时，以及压缩遗漏或提前收尾问题。自动化测试与真实任务结果分别记录。
